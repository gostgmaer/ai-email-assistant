# v2.0 Implementation Plan — Deployment & Collaboration

This is the technical follow-up to [`roadmap.md`](./roadmap.md#-v20--enterprise-ai-workspace)'s v2.0 section. That doc calls v2.0 "Enterprise AI Workspace" and bundles Multi-tenancy and Enterprise Features (RBAC, Audit Logs, SSO, SCIM) in with everything else — this plan **splits that**: Multi-tenancy and Enterprise Features move to v3.0, and v2.0 becomes Client Deployment + Collaboration + Automation + AI Agents, built on the existing single-tenant (`User`-scoped) data model wherever possible.

## Why the split

Every service in the codebase today enforces ownership the same way: `getOwnedAccountOrThrow(userId, accountId)` / `getOwnedTaskWithMessage(userId, taskId)`, scoping by a single `userId` foreign key. There is no `Organization`, `Workspace`, or `role` concept anywhere in `schema.prisma`. Full multi-tenancy (orgs, invitations, RBAC, SSO, SCIM, audit logs, cross-org data isolation) is a foundational data-model change that everything else would need to be rebuilt on top of — doing it now would block v2.0's actual value (deployment, shared inbox, automation, agents) behind a much larger effort. v3.0 gets to do multi-tenancy properly, once; v2.0 doesn't need to.

**Working decision: "Shared Inbox" in v2.0 means account-level sharing, not organizations.** A new join table grants specific users access to a specific `EmailAccount` (with a role), independent of any org/workspace concept. This delivers the actual feature ("my co-founder and I both work out of support@company.com") without inventing tenancy. Section 2 below covers this in detail — it's the single biggest architectural change in this plan, bigger than deployment.

## 1. Client Deployment

**Already built:** production Dockerfiles for all four services (`api`, `ai`, `web`, `worker`), a working `docker-compose.yml`, `NODE_ENV=production` builds, health check endpoint, structured logging. Nothing here is prototype-quality — it's actually deploy-ready as Docker images today.

**Net new:**
- A hosted target. Recommendation: **Railway** — deploys straight from the existing per-service Dockerfiles, managed Postgres supports `CREATE EXTENSION vector` (needed for the pgvector/HNSW RAG index) unmodified, managed Redis, private networking between services, GitHub-push auto-deploy. Render is the fallback if flat pricing matters more than Railway's usage-based model.
- Secrets management: today all config is `.env` files (`apps/api/.env`, etc.) mounted into containers. Needs migrating to the host's secret store (Railway environment variables per service) — nothing in the app needs to change, just how config reaches it.
- CI: `.github/` is currently empty. Add a workflow that runs `tsc --noEmit` + `jest` (both now green, 8/8 suites) on every PR before merge — this is also the thing that would have caught the circular-import bug found and fixed in this session, had it existed then.
- A deploy doc (host setup, env var list per service, migration-on-deploy step for `prisma migrate deploy`, rollback procedure).

**Explicitly out of scope for this phase:** autoscaling, multi-region, blue/green deploys — single-instance-per-service is fine at current usage.

## 2. Shared Inbox / Collaboration

**Already built:** nothing shared — `EmailAccount.userId` is a single required foreign key, enforced everywhere via `getOwnedAccountOrThrow`.

**Design decision:** add an `AccountMember` model (`accountId`, `userId`, `role: OWNER | MEMBER`) alongside the existing `EmailAccount.userId` (which becomes "the connector/owner," kept for OAuth-token ownership and backward compat). An account is accessible to a user if they own it *or* have an `AccountMember` row.

This is not a small change — it touches every service that currently does an ownership check:
- `EmailAccountService`, `CalendarAccountService`, `InboxService`, `ComposeService`, `TasksService` (for tasks tied to a shared account's threads), `AiProcessingProcessor` (whose auto-send/auto-schedule settings currently live on `EmailAccount` — need to decide if those apply per-account or per-member).
- Every `getOwnedXOrThrow(userId, id)` needs an equivalent `getAccessibleXOrThrow(userId, id)`, checking membership instead of strict `userId` equality. Recommend doing this as a single sweep once the `AccountMember` model exists, not incrementally per feature — a mixed state (some endpoints check membership, others still check strict ownership) is worse than either extreme.

**Feature scope for v2.0** (roadmap.md's "Collaboration" section):
- Shared Inbox: multiple users see and act on the same `EmailAccount`'s threads (needs the access-model change above).
- Assign Conversations: new `EmailThread.assignedToUserId` (nullable, must be an `AccountMember` of that thread's account).
- Internal Notes: new `ThreadNote` model (`threadId`, `authorId`, `body`, `createdAt`) — visible only to account members, never sent to the external party. Straightforward, no dependency on anything else in this section.
- Shared Drafts: an AI-drafted or manually-composed reply becomes visible/editable by any account member before send, not just the original recipient — mostly a query-scope change on the existing draft-reply flow (`EmailMessage.inReplyToMessageId` drafts) once membership exists.
- Team Ownership: covered by Assign Conversations + the membership model; no separate work.

**Invitations:** a lightweight version (invite a user by email to become an `AccountMember` of one specific account) is in scope. Org-wide invitations are not — that's the v3.0 multi-tenancy piece.

## 3. Automation (Workflow Builder)

**Already built:** the AI processing pipeline (`AiProcessingProcessor`) already does trigger→condition→action for exactly one hardcoded case — classify, then `isSafeToAutoSend` checks (`!spam && priority !== 'urgent' && account.autoSendCategories.includes(category)`), then send. The `EmailAccount.autoScheduleMeetings` toggle added this session is the same shape again for a different action. The pattern already exists three times; it's just not user-configurable or generalized.

**Net new — a real rules engine:**
- `WorkflowRule` model: `accountId`, `trigger` (`NEW_MESSAGE` to start — matches what the pipeline already runs on), `conditions` (JSON: category/priority/sender-pattern/keyword, evaluated against the same `ClassificationResult` already computed), `actions` (ordered list: `AUTO_REPLY`, `FORWARD`, `ADD_LABEL`, `CREATE_TASK`, `ASSIGN_TO` (depends on §2's membership model), `NOTIFY`).
- Evaluation point: after classification, before the existing auto-send/auto-schedule logic in `AiProcessingProcessor` — replace the two hardcoded `isSafeToAutoSend`/`autoScheduleMeetings` checks with rule evaluation, and migrate today's `autoSendCategories`/`autoScheduleMeetings` settings into equivalent default `WorkflowRule` rows so existing user configuration isn't lost.
- Approval Chains / AI Escalation: an action type (`REQUIRE_APPROVAL`) that holds the pipeline's output as a draft (already the default behavior when auto-send doesn't apply) rather than a new mechanism — "escalation" is "assign + notify a specific person," which composes from actions already listed above.
- Builder UI: start with a structured form (trigger + condition rows + action rows), not a drag-drop canvas — matches the MVP's "ship the smallest real version first" pattern used throughout this codebase (e.g., meeting scheduling shipped as a review-and-confirm form, not a calendar-picker widget).

Rules Engine is the prerequisite for Auto Classification/Auto Routing — both are just specific `(condition, action)` pairs once the engine exists, not separate work.

## 4. AI Agents

**Already built:** the capability pattern in `apps/ai` (`schemas.py`/`state.py`/`nodes.py`/`graph.py`, registered in a `*_service.py` singleton, routed via FastAPI, registered in `main.py`) is exactly the extensibility point this needs. `meeting_time`, `extract`, `classify`, `reply` are all instances of it already.

**What "Customer Support Agent" / "Sales Agent" / etc. actually are:** not new infrastructure — a named persona (system prompt + tone + allowed actions) layered on the existing reply-generation and task-extraction capabilities, scoped to an `EmailAccount` or a `WorkflowRule`'s `AUTO_REPLY` action. Concretely:
- `Agent` model: `name`, `accountId`, `systemPrompt`, `allowedActions` (subset of §3's action types), `enabled`.
- `AiClientService.generateReply()` gains an optional `agentId` param that swaps in the agent's system prompt instead of the default reply prompt — additive, doesn't change existing callers.
- "Executive Assistant" is the interesting one — it's the closest to true multi-step autonomy (triage → draft → schedule → follow up), which is what §3's Workflow Builder already provides once an agent is attached to a rule's actions rather than a single reply call.

**Recommend deferring:** a generic "build your own agent" system prompt editor is easy to ship; genuinely autonomous multi-step agents (beyond what a `WorkflowRule` chain already does) are a bigger LangGraph investment and should wait for real usage data on which personas people actually want.

## 5. Integrations & Analytics (stretch, not core v2.0)

Both are called out in `roadmap.md` under v2.0 but don't block or get blocked by anything above:

- **Integrations** (Slack, Teams, Jira, Notion, Linear, HubSpot, Salesforce, Discord): each is an independent OAuth-connect + webhook/API-call integration, same shape as the existing Google/Microsoft connect flows. No shared infrastructure work — pick one (Slack is the highest-value first target: "notify Slack when a thread is assigned to you" reuses §2's assignment event) and build it end-to-end as the template for the rest, rather than building a generic "integrations framework" speculatively.
- **Analytics** (response time, inbox health, productivity metrics, team performance, SLA tracking): per-user metrics (response time, inbox health) can ship from data that already exists (`EmailMessage.receivedAt`, thread reply timestamps) with no new capture work. Team-scoped metrics (team performance, SLA tracking) depend on §2's assignment/membership model existing first.

Recommend treating both as backlog items to pull from once §1–4 ship, not a committed part of this phase.

## Suggested sequencing

1. **Client Deployment** (§1) — no dependencies, de-risks everything after it by giving every subsequent feature a real environment to land in, and CI catches regressions like this session's circular-import bug going forward.
2. **Shared Inbox access model** (§2's `AccountMember` + the ownership→membership sweep) — the biggest single change; doing it early means §3/§4's `ASSIGN_TO`/team features build on a stable foundation instead of retrofitting later.
3. **Workflow Builder core** (§3) — rules engine + the structured builder UI, migrating today's `autoSendCategories`/`autoScheduleMeetings` into it.
4. **Shared Inbox features** (§2's Assign/Notes/Shared Drafts) — now that both the access model (#2) and the assignment-capable rules engine (#3) exist.
5. **AI Agents** (§4) — personas layered on existing capabilities, lowest risk of this list, do last since it benefits from the Workflow Builder's action list being final.
6. **Integrations/Analytics** (§5) — pull individual items from backlog as needed, not a blocking phase.

## Open decisions to make before starting

- Confirm Railway vs. Render for deployment (plan above recommends Railway; needs an account + billing decision that's the user's to make, not mine to provision).
- `AccountMember` roles: is `OWNER`/`MEMBER` sufficient for v2.0, or is a third tier (e.g. read-only `VIEWER`) needed at launch? Recommend starting with two roles — a third is additive later, removing one after users depend on it is not.
- Do `autoSendCategories`/`autoScheduleMeetings` get hard-migrated into `WorkflowRule` rows (one-time migration, then removed as standalone columns) or kept as a fast-path alongside the general rules engine? Recommend hard migration — two overlapping mechanisms for the same thing is the kind of drift that caused this session's stale-`MVP.md` confusion.
- Which single integration (§5) to build first as the template, if any lands in this phase at all.
