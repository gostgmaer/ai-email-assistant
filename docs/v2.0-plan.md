# v2.0 Implementation Plan — Deployment & Collaboration

This is the technical follow-up to [`roadmap.md`](./roadmap.md#-v20--enterprise-ai-workspace)'s v2.0 section. That doc calls v2.0 "Enterprise AI Workspace" and bundles everything — Multi-tenancy, Enterprise Features, Integrations, and Analytics — in with Collaboration/Automation/AI Agents. This plan **splits that**: v2.0 is Client Deployment + Collaboration + Automation + AI Agents, built on the existing single-tenant (`User`-scoped) data model. **Multi-tenancy, Enterprise Features, Integrations, and Analytics all move to v3.0** — see "What actually moved to v3.0" below for why the latter two joined the split.

**Status: §1–4 shipped and verified live.** The one item still open in v2.0's own scope is pre-built Agent templates for the five personas `roadmap.md` names (§4 below) — the persona *system* is done, but nothing ships pre-configured yet.

## What actually moved to v3.0

- **Multi-tenancy, Enterprise Features** — see "Why the split" below; this was the original call.
- **Integrations, Analytics** — originally scoped as "stretch, not core v2.0" (§5, kept below for its technical notes), then moved to v3.0 outright once §1–4 shipped and neither had started. Nothing about them changed technically; they just never became load-bearing for anything else in v2.0, so there's no reason to keep them formally "in scope" for a version that's otherwise done.
- **True multi-step Approval Chains** — `roadmap.md`'s Automation section lists this alongside Workflow Builder. What shipped (§3) is a single binary gate (`REQUIRE_APPROVAL`: auto-send vs. hold-as-draft), not sequential multi-person approval (e.g. "needs sign-off from manager, then director"). That's a genuinely bigger feature (an approval-state machine, not just another action type) — v3.0.

## Why the split

Every service in the codebase today enforces ownership the same way: `getOwnedAccountOrThrow(userId, accountId)` / `getOwnedTaskWithMessage(userId, taskId)`, scoping by a single `userId` foreign key. There is no `Organization`, `Workspace`, or `role` concept anywhere in `schema.prisma`. Full multi-tenancy (orgs, invitations, RBAC, SSO, SCIM, audit logs, cross-org data isolation) is a foundational data-model change that everything else would need to be rebuilt on top of — doing it now would block v2.0's actual value (deployment, shared inbox, automation, agents) behind a much larger effort. v3.0 gets to do multi-tenancy properly, once; v2.0 doesn't need to.

**Working decision: "Shared Inbox" in v2.0 means account-level sharing, not organizations.** A new join table grants specific users access to a specific `EmailAccount` (with a role), independent of any org/workspace concept. This delivers the actual feature ("my co-founder and I both work out of support@company.com") without inventing tenancy. Section 2 below covers this in detail — it's the single biggest architectural change in this plan, bigger than deployment.

## 1. Client Deployment — ✅ done

**Already built:** production Dockerfiles for all four services (`api`, `ai`, `web`, `worker`), a working `docker-compose.yml`, `NODE_ENV=production` builds, health check endpoint, structured logging. Nothing here is prototype-quality — it's actually deploy-ready as Docker images today.

**Net new:**
- A hosted target: **self-hosted VM / dedicated server**, not a PaaS. `docker-compose.prod.yml` (standalone, not an override — see its header comment for why) runs the full stack plus a `caddy` reverse proxy that terminates TLS via Let's Encrypt automatically; only `caddy` publishes ports to the host, everything else — including Postgres/Redis — stays on the internal Docker network.
- Secrets management: `.env` files per service, same convention as dev, plus a root `.env` for the values `docker-compose.prod.yml` interpolates (`POSTGRES_PASSWORD`, `DOMAIN`, `API_DOMAIN`, `NEXT_PUBLIC_API_URL`, `ACME_EMAIL`) — see `docs/deployment.md`.
- CI: `.github/workflows/ci.yml` runs `tsc --noEmit` + `jest` + `pytest` on every PR/push to `master` — this is also the thing that would have caught the circular-import bug found and fixed earlier in this session, had it existed then. `.github/workflows/deploy.yml` is separate, manually triggered (`workflow_dispatch`, not push-to-deploy — a production deploy shouldn't fire just because someone pushed to master), and SSHes in to run `scripts/deploy.sh`.
- `scripts/deploy.sh`: pull latest `master`, rebuild, `prisma migrate deploy`, restart, wait for `api` healthy, prune old images — the same script whether run manually or from CI.
- A deploy doc (`docs/deployment.md`): server prep, DNS, env var list per service, first-deploy steps, ongoing deploys, rollback, backups.

**Explicitly out of scope for this phase:** autoscaling, multi-region, blue/green deploys, automated off-box backup shipping — single VM / single-instance-per-service is fine at current usage.

## 2. Shared Inbox / Collaboration — ✅ done

**Already built:** nothing shared — `EmailAccount.userId` is a single required foreign key, enforced everywhere via `getOwnedAccountOrThrow`.

**Design decision:** add an `AccountMember` model (`accountId`, `userId`, `role: OWNER | MEMBER`) alongside the existing `EmailAccount.userId` (which becomes "the connector/owner," kept for OAuth-token ownership and backward compat). An account is accessible to a user if they own it *or* have an `AccountMember` row.

This is not a small change — it touches every service that currently does an ownership check:
- `EmailAccountService`, `CalendarAccountService`, `InboxService`, `ComposeService`, `TasksService` (for tasks tied to a shared account's threads), `AiProcessingProcessor` (whose auto-send/auto-schedule settings currently live on `EmailAccount` — need to decide if those apply per-account or per-member).
- Every `getOwnedXOrThrow(userId, id)` needs an equivalent `getAccessibleXOrThrow(userId, id)`, checking membership instead of strict `userId` equality. Recommend doing this as a single sweep once the `AccountMember` model exists, not incrementally per feature — a mixed state (some endpoints check membership, others still check strict ownership) is worse than either extreme.

**Feature scope for v2.0** (roadmap.md's "Collaboration" section):
- Shared Inbox: multiple users see and act on the same `EmailAccount`'s threads (needs the access-model change above).
- Assign Conversations: new `EmailThread.assignedToUserId` (nullable, must be an `AccountMember` of that thread's account).
- Internal Notes: new `ThreadNote` model (`threadId`, `authorId`, `body`, `createdAt`) — visible only to account members, never sent to the external party. Straightforward, no dependency on anything else in this section.
- Shared Drafts: an AI-drafted or manually-composed reply becomes visible/editable by any account member before send, not just the original recipient — mostly a query-scope change on the existing draft-reply flow (`EmailMessage.inReplyToMessageId` drafts) once membership exists.
- Team Ownership: covered by Assign Conversations + the membership model; no separate work.

**Invitations:** a lightweight version (invite a user by email to become an `AccountMember` of one specific account) is in scope. Org-wide invitations are not — that's the v3.0 multi-tenancy piece.

## 3. Automation (Workflow Builder) — ✅ done (Approval Chains partially — see "What actually moved to v3.0")

**Already built:** the AI processing pipeline (`AiProcessingProcessor`) already does trigger→condition→action for exactly one hardcoded case — classify, then `isSafeToAutoSend` checks (`!spam && priority !== 'urgent' && account.autoSendCategories.includes(category)`), then send. The `EmailAccount.autoScheduleMeetings` toggle added this session is the same shape again for a different action. The pattern already exists three times; it's just not user-configurable or generalized.

**Net new — a real rules engine:**
- `WorkflowRule` model: `accountId`, `trigger` (`NEW_MESSAGE` to start — matches what the pipeline already runs on), `conditions` (JSON: category/priority/sender-pattern/keyword, evaluated against the same `ClassificationResult` already computed), `actions` (ordered list: `AUTO_REPLY`, `FORWARD`, `ADD_LABEL`, `CREATE_TASK`, `ASSIGN_TO` (depends on §2's membership model), `NOTIFY`).
- Evaluation point: after classification, before the existing auto-send/auto-schedule logic in `AiProcessingProcessor` — replace the two hardcoded `isSafeToAutoSend`/`autoScheduleMeetings` checks with rule evaluation, and migrate today's `autoSendCategories`/`autoScheduleMeetings` settings into equivalent default `WorkflowRule` rows so existing user configuration isn't lost.
- Approval Chains / AI Escalation: an action type (`REQUIRE_APPROVAL`) that holds the pipeline's output as a draft (already the default behavior when auto-send doesn't apply) rather than a new mechanism — "escalation" is "assign + notify a specific person," which composes from actions already listed above.
- Builder UI: start with a structured form (trigger + condition rows + action rows), not a drag-drop canvas — matches the MVP's "ship the smallest real version first" pattern used throughout this codebase (e.g., meeting scheduling shipped as a review-and-confirm form, not a calendar-picker widget).

Rules Engine is the prerequisite for Auto Classification/Auto Routing — both are just specific `(condition, action)` pairs once the engine exists, not separate work.

## 4. AI Agents — ✅ persona system done; pre-built templates pending

**Built:** `Agent` model (`accountId`, `name`, `systemPrompt`, `enabled`) — a named persona layered on the existing reply capability, not new generation infrastructure. `ReplyRequest.system_prompt_override` (apps/ai) replaces `reply.md`'s default prompt entirely when set, verified against a real LLM call with a deliberately distinctive persona to confirm the override actually changes the model's output, not just that the field round-trips. `WorkflowRule`'s `AUTO_REPLY` action carries an optional `agentId`; rule evaluation happens *before* reply generation (not after, where the old auto-send decision was made) specifically so the persona can shape the reply's actual wording. Owner-only CRUD + a frontend panel to create/edit personas and pick one in the Workflow rule builder.

**What's still open:** the five personas `roadmap.md` names — Customer Support Agent, Sales Agent, HR Agent, Finance Agent, Executive Assistant — don't exist as ready-made options. The generic persona system supports all of them today, but a user has to hand-write each one's prompt from scratch. Closing this means shipping five well-written starter prompts as a "start from template" picker in the Agent creation form (pure frontend — pre-fills name/systemPrompt, still requires the user to review and click Create, consistent with this app's human-in-the-loop posture elsewhere). No backend change needed.

- Executive Assistant's prompt should lean into what's actually different about it: not a "wittier reply," but instructions that make sense when the agent is attached to a rule with `ASSIGN_TO`/`NOTIFY` actions alongside `AUTO_REPLY` — triage/coordinate framing, not just tone.
- Genuinely autonomous multi-step agents (beyond what a `WorkflowRule` chain already provides) remain out of scope — that's a bigger LangGraph investment, worth waiting for real usage data on which personas people actually reach for before building.

## 5. Integrations & Analytics — moved to v3.0

Originally scoped here as "stretch, not core v2.0." Now that §1–4 are done and neither of these ever became a dependency for anything else in v2.0, they've moved to v3.0 outright rather than lingering as an open "maybe" on an otherwise-finished version. The technical notes from the original scoping still apply whenever this gets picked up:

- **Integrations** (Slack, Teams, Jira, Notion, Linear, HubSpot, Salesforce, Discord): each is an independent OAuth-connect + webhook/API-call integration, same shape as the existing Google/Microsoft connect flows. No shared infrastructure work — pick one (Slack is the highest-value first target: "notify Slack when a thread is assigned to you" reuses §2's assignment event, which now exists) and build it end-to-end as the template for the rest, rather than building a generic "integrations framework" speculatively.
- **Analytics** (response time, inbox health, productivity metrics, team performance, SLA tracking): per-user metrics (response time, inbox health) can ship from data that already exists (`EmailMessage.receivedAt`, thread reply timestamps) with no new capture work. Team-scoped metrics (team performance, SLA tracking) can now build on §2's assignment/membership model, which exists.

## Decisions made

- **Deployment target: your own VM / dedicated server** (originally scoped as Railway; changed once the user decided to self-host instead — see §1 and `docs/deployment.md`). Docker Compose + Caddy (automatic TLS) replaces Railway's managed Postgres/Redis/networking; provisioning the actual server/DNS is still the user's action.
- **`AccountMember` roles: two (`OWNER`/`MEMBER`)**, no `VIEWER` tier — kept simple, additive later if needed.
- **`autoSendCategories`/`autoScheduleMeetings`: hard-migrated.** `autoSendCategories` became one `WorkflowRule` row per category (verified via the actual migration backfill, not just planned); `autoScheduleMeetings` stayed its own toggle by design — it's driven by task extraction (`MEETING_REQUEST`), a different trigger than `WorkflowRule`'s classify-based `NEW_MESSAGE` evaluation, and forcing both into one engine in a single pass would've been unnecessarily risky.
- **Remaining open decision:** which single integration to build first as the template, whenever v3.0's Integrations work starts (Slack remains the recommendation — reuses the assignment event that now exists).
