# v1.2 Implementation Plan — Productivity Suite

This is the technical follow-up to the feature list in [`roadmap.md`](./roadmap.md#-v12--productivity-suite). That doc says *what* v1.2 covers; this doc says *how*, grounded in what the codebase already has versus what's actually new — several v1.2 items are much smaller than they look because v1.1 already built the underlying piece and never wired it up.

## v1.1 status (as of this writing)

Complete: document cleanup (stale-`PROCESSING` → `FAILED` cron), HTML/structure-aware parsing, MMR re-ranking on document search, and a RAG retrieval eval harness (`apps/api/scripts/rag-eval.ts`). The async upload architecture (NestJS upload-only → BullMQ → AI service downloads/parses/embeds) was verified live end-to-end for 8 of 11 supported formats (pdf, docx, txt, md, html, csv, json, xml). `.xlsx`, `.eml`, `.msg` are implemented but not yet verified against a live upload (blocked on `file-upload-service`'s own rate limit during testing, not a known defect).

## Two findings that change the v1.2 estimate

1. **`docs/roadmap.md`'s MVP section is stale.** It says "Connect one email account per provider," but the schema (`User.emailAccounts EmailAccount[]`) and `EmailAccountService.connectOAuthAccount` already support unlimited accounts per user per provider, each with its own credentials and settings. Multi-account is not new work — it's mostly UI and documentation.
2. **`apps/ai` already has a working task/meeting extraction capability that `apps/api` never calls.** `POST /email/extract` (`apps/ai/app/capabilities/extract/`) returns `tasks` and `meeting_requests` per thread today. `AiClientService` has no method for it and `AiProcessingProcessor` never invokes it. A large chunk of "AI Task Extraction" is wiring, not building.

## 1. Multiple Accounts / Unified Inbox

**Already built:** per-user `EmailAccount[]`, per-account `EmailCredential`, per-account sync settings, connect flow that upserts by `(provider, email)`, background sync fan-out over all `syncEnabled` accounts. `InboxService.listThreads` already resolves to "all of this user's accounts" when `accountId` is omitted (the `where` clause simply drops an `undefined` filter) — worth a targeted test to confirm this is correct today, not assumed.

**Actual v1.2 work:**
- Frontend: account switcher / "all accounts" toggle, per-message account badge in thread list and detail view, per-account settings screen (already have the API surface via `GET /email-accounts`).
- Cross-account correctness: pagination and sort order when merging threads from multiple accounts (currently untested at that scale); confirm `ContactMemory` (already keyed by `userId`, not `accountId`) behaves sensibly when the same contact emails two of the user's connected accounts.
- **Decided: no multi-tenancy in v1.2.** The schema's global `@@unique([provider, email])` constraint stays as-is — it correctly prevents account hijacking, and "multiple accounts" here means multiple accounts *per user*, not shared/team inboxes. Multi-tenancy remains v2.0-only; nothing in this plan depends on or blocks it.
- Correct the MVP section of `roadmap.md`.

No migrations required.

## 2. Calendar Integration

**Nothing exists yet** — no `Calendar`/`CalendarAccount` model, no calendar OAuth scopes requested anywhere, no AI capability.

**Design decision to make explicitly before starting:** connect calendar as its own OAuth flow, separate from mail. The codebase already has precedent for this split (`apps/api/src/modules/oauth` for login vs. `apps/api/src/modules/email-account/strategies` for mail-connect are two independent strategy sets with different scopes). Reuse that shape:
- New `GoogleCalendarConnectStrategy` / `MicrosoftCalendarConnectStrategy` requesting `https://www.googleapis.com/auth/calendar.events` (or narrower, if only free/busy + create is needed) and the Graph Calendar equivalent.
- Do **not** fold calendar scopes into the existing mail-connect strategies — that would force re-consent on every existing connected account and couples two things the user should be able to grant independently.
- New `CalendarAccount` + `CalendarCredential` models, mirroring `EmailAccount`/`EmailCredential`'s shape (encrypted tokens via the existing `EncryptionService`, same lazy-refresh-on-expiry pattern as `EmailAccountService.getValidAccessToken`).
- Confirm `access_type=offline` / `prompt=consent` behavior for Google before building — current mail-connect strategy options weren't confirmed to request offline access explicitly; verify refresh tokens are actually being issued for calendar scopes, not just access tokens.

**Phasing within v1.2** (this is the largest single item — consider splitting across two sprints):
1. Connect flow + credential storage + a read-only capability (availability lookup) first — lowest risk, proves the OAuth flow end-to-end.
2. Create/schedule meetings (write path) — needs explicit confirmation UX before sending a calendar invite (same "human approval before sending" principle already applied to AI-drafted email replies).
3. Meeting suggestions — this is the only sub-feature that's genuinely AI work: a new `apps/ai/app/capabilities/scheduling/` capability taking thread content + both parties' availability, proposing time slots. Everything upstream of it (OAuth, availability fetch) has to exist first.

New queue: none strictly required for read/write calendar actions (they're synchronous user-initiated API calls, not background jobs), but availability lookups for meeting suggestions may be worth caching/prefetching via a job if latency matters.

## 3. Productivity Features

Ordered roughly by how much is already built vs. net-new.

### AI Task Extraction / Action Items — mostly wiring
- Add `extract()` to `AiClientService` (mirror the existing `classify()` method's shape).
- Call it from `AiProcessingProcessor`, either as another step in the existing per-message pipeline (bundled with classify/contact-memory) or as its own `AIJobs.ExtractTasks` job if it should be independently retriggerable/optional per user setting.
- **Decide the storage shape before migrating**: a JSON blob on `EmailMessage` (precedent: `generationMetadata Json?`) is fastest to ship, but "Action Items" implies checkable/sortable/reminder-able items — that wants a normalized `Task` model (`id, userId, emailMessageId, description, dueDate, status, completedAt`), following the `Document`/`DocumentChunk` precedent for structured data instead of a blob. Recommend the normalized model — Smart Reminders (below) needs to query "tasks due soon" efficiently, which a JSON column can't index.
- Idempotency: reuse the `aiProcessedAt` pattern, or add `tasksExtractedAt` if extraction should be independently re-run without re-running classify/reply-gen.

### Priority Inbox — cheap win
- `ClassificationResult` (category/priority/sentiment) is already computed by the classify capability on every processed message and currently thrown away. Add `priority`, `category`, `sentiment` columns to `EmailMessage` (or a separate `EmailClassification` table if these need their own audit history) and persist what's already being computed — no new AI work.
- `InboxService.listThreads` gets a priority sort/filter option once the column exists.

### Snooze Emails — small, self-contained
- New nullable `EmailThread.snoozedUntil DateTime?`.
- `InboxService.listThreads`'s default view filters out threads where `snoozedUntil > now()`.
- New repeatable job (same `upsertJobScheduler` pattern as `scheduleBackgroundSync`/`scheduleDocumentCleanup`) that periodically clears expired `snoozedUntil` values (or the filter alone may be sufficient without a job, if "resurface" just means "stop hiding it" — a job is only needed if resurfacing should trigger a notification).

### Smart Reminders / Daily Email Digest — new scheduled jobs, reuse existing fan-out pattern
- Both follow `EmailSyncProcessor.runBackgroundScan`'s shape: a repeatable job (digest: cron pattern like `0 8 * * *`, which would be this codebase's first cron-pattern repeatable job — everything today uses fixed `every` intervals) that queries all eligible users/threads and fans out one job per user.
- Digest content is a straightforward aggregation query (unread count, priority threads, extracted tasks due) — no new AI capability needed if Priority Inbox and Task Extraction above ship first; digest is consumption of their output, not new generation, unless a narrative/summary digest ("here's what happened today") is wanted, which would reuse the existing summarize capability.
- Standardize `@OnWorkerEvent('failed')` handling across processors while adding these — it's currently inconsistent (present on `EmailSyncProcessor`, absent on `NotificationProcessor`/`AiProcessingProcessor`), and a silently-failing digest job is worse than a silently-failing sync job (sync retries next cycle regardless; a missed digest just never gets noticed).

### Follow-up Suggestions — the one genuinely new AI capability
- No existing capability covers this. Reasonable v1: reuse Task Extraction's `meeting_requests`/`tasks` output plus thread state (awaiting-reply detection: last message direction + elapsed time) as input signals, rather than a new LLM call from scratch — likely a rules/heuristic pass over already-extracted structured data before reaching for a new prompt.

## Suggested sequencing

1. **Multi-account UI polish** (no backend risk, ships fast, corrects the stale roadmap claim).
2. **Task Extraction wiring + Priority Inbox** (both are "persist what's already computed" — cheapest real value in v1.2).
3. **Snooze** (small, self-contained, no dependencies on the above).
4. **Smart Reminders / Daily Digest** (depends on #2 for meaningful content).
5. **Calendar Integration** (largest, most new infrastructure, least dependent on the others — can run in parallel with 2-4 if there's a second engineer).
6. **Follow-up Suggestions** (depends on #2's extraction output; do last).

## Open decisions to make before starting

- Task storage: normalized `Task` model vs. JSON blob (recommendation above: normalized).
- Calendar OAuth: confirm Google issues refresh tokens for the new scope under this app's current consent-screen configuration before assuming the existing lazy-refresh pattern just works unmodified.
- Whether snooze needs an active "resurface" job or is purely a query-time filter.
- Whether the digest is data-only or includes an LLM-generated narrative summary (affects whether it's an `apps/ai` capability or pure `apps/api` aggregation).
